# Governance

Telltales is an open-source project engineered and maintained through an **AI-led process with human direction and oversight**. This document describes the public decision model that is operating today. It does not promise committees, elections, maintainer tiers or other institutions that do not yet exist.

## Decision authority

The repository owner and authorised maintainers retain final authority over project purpose, scope, merges, releases, safety claims and other consequential public decisions.

AI agents may investigate the repository, propose changes, implement authorised work, run or inspect validation, and explain their reasoning and evidence. They do not independently acquire authority to redefine the project, make external commitments, publish releases, or turn an experiment into a trusted navigation system.

Human direction is therefore part of the system, not an exception to it. Human participants may set goals and constraints, supply domain evidence, review outcomes, challenge assumptions and withhold authority for consequential steps.

## How decisions are made

Decisions should be driven by the project's purpose, observed usefulness, technical evidence and the cost of changing direction. The preferred pattern is a focused issue or other durable public requirement, followed by repository inspection, a coherent implementation batch, validation, and a public record of what changed and what remains uncertain.

The project distinguishes demonstrated behaviour from ambition. A feature is not treated as supported merely because it is plausible, configured as a candidate, or described as a future possibility. Claims about sensors, protocols, safety, calibration and real-world sailing use should be backed by evidence appropriate to the claim.

When alternatives are reasonable, maintainers may choose the smallest approach that preserves clear contracts and leaves room to learn. Existing architecture is not protected for its own sake.

## AI-led maintenance

AI-led maintenance means that AI agents are expected to do most routine implementation and editorial work. Their output is reviewed through tests, repository state, issue requirements, human feedback and real-world evidence rather than accepted because it was generated by AI.

The project does not claim fully autonomous software development. The amount of autonomy demonstrated is the amount visible in completed, reviewed and validated work.

Conventional human-authored implementation is not the intended primary development path. External code can still be valuable as a prototype, counterexample or concrete proposal, but maintainers may rework or reimplement it within the AI-led process to preserve consistency and reviewability.

## Public participation

Anyone can report bugs, propose features or use cases, share test evidence, review changes, question assumptions, or challenge a decision in GitHub issues and pull-request discussions where applicable.

Input is evaluated by relevance and evidence, not by whether it came from a human or an AI. Particularly useful contributions include reproducible failures, screenshots or recordings that expose display behaviour, protocol samples that can be shared safely, browser/display compatibility results, sailing-domain corrections, and clear explanations of why an existing decision causes a real problem.

Discussion can change a decision. There is no promise that every proposal will be implemented, that every patch will be merged as written, or that a particular participant will receive an ongoing project role.

## Engineering and review expectations

Changes should keep behaviour and claims aligned. In particular:

- preserve observation identity, provenance and unavailable/failure semantics rather than presenting unsupported values as measured truth;
- keep protocol/source concerns separate from reusable presentation where the current architecture provides that seam;
- add or update tests for behavioural changes and run the relevant existing checks;
- keep public documentation sufficient for contributors to understand supported behaviour without private context;
- avoid speculative frameworks, hidden dependencies and roadmap commitments that are not justified by current needs;
- treat navigation- or safety-related claims conservatively.

Documentation-only changes should still be checked against the current repository so commands, links and capability claims remain true.

## Changes to governance

This governance model may evolve as the project earns a need for additional roles or process. Material governance changes should be public, explicit and consistent with [CONTRIBUTING.md](CONTRIBUTING.md). They should describe practice that actually exists rather than announcing structure in advance of need.
